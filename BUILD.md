# Build and CI

## Authoritative build

All authoritative builds run on GitHub Actions runners. The host operating system is only an editing interface; it is not part of the release process. A local build never substitutes for a green workflow run.

### CI workflow

`.github/workflows/ci.yml` runs on:

- pushes to `develop`;
- pull requests targeting `develop` or `main`;
- manual `workflow_dispatch`.

It performs:

1. Checkout.
2. Temurin JDK 17.
3. Android SDK via `android-actions/setup-android@v3`, with its retired default `tools` package disabled via `packages: ''`.
4. Pinned `platforms;android-37.2`, `build-tools;36.0.0` and `platform-tools` installed explicitly.
5. Gradle wrapper 9.9.2 via `gradle/actions/setup-gradle@v4`, with dependency caching enabled.
6. Dependency-resolution validation for `debugRuntimeClasspath`.
7. `testDebugUnitTest`, `lint` and `assembleDebug`.
8. Upload of test/lint reports and the debug APK as workflow artefacts, retained for 14 days.

A pull request is not mergeable until this workflow passes. The actual outcome is reported on the workflow run and on the commit status.

### Release workflow

`.github/workflows/release.yml` runs on:

- version tags matching `v*` (for example `v0.1.0`);
- manual `workflow_dispatch` with an explicit existing tag and an optional `rebuild` flag.

No release tag is created during Phase 1. Publishing any release requires explicit project-owner approval.

The release job:

1. Resolves and validates the target ref as semantic `MAJOR.MINOR.PATCH`.
2. Checks out the exact immutable tagged commit.
3. Verifies that `versionName` in `app/build.gradle.kts` matches the tag; `versionCode` must be incremented consistently for every version change.
4. Refuses to overwrite an existing release unless `rebuild=true` is explicitly supplied.
5. Requires the secrets `KEYSTORE_BASE64`, `SIGNING_STORE_PASSWORD`, `SIGNING_KEY_ALIAS` and `SIGNING_KEY_PASSWORD`.
6. Decodes the keystore only into the runner's temporary directory.
7. Validates dependency resolution and confirms no signing material is tracked in Git.
8. Runs the complete unit test suite and lint.
9. Builds a signed release APK and AAB.
10. Verifies both signatures with `apksigner` and `jarsigner`.
11. Generates `SHA256SUMS.txt` and versioned release notes.
12. Publishes APK, AAB, checksums, notes and lint report to GitHub Releases with `overwrite_files: false`.
13. Retains verification reports as a workflow artefact for 30 days.

### Versioning and rebuilds

Versions use semantic versioning. The current foundation is `0.1.0` with `versionCode = 1`. A build succeeding is not a release decision.

A manual rebuild of tag `vX.Y.Z` with `rebuild=true` publishes a separate release tagged `vX.Y.Z-rebuild-<run number>` that points at the same immutable commit. The original release, its tag and its artefacts are never modified. Use a new patch version tag instead when the rebuild contains a code change.

### Signing key management

The production signing key is not generated by CI and is never stored in the repository. It must be generated once, encrypted at rest outside GitHub, and backed up securely with access restricted to the project owner. The four secrets above are the only channel through which the runner receives it. To recover or rotate the key, update the repository secrets and verify a fresh release run; never create a new key for a rebuild of an existing version.

## Optional local build

Requires JDK 17, Android SDK platform 37.2, build-tools 36.0.0 and a command-line shell.

```powershell
.\gradlew --no-daemon testDebugUnitTest
.\gradlew --no-daemon lint
.\gradlew --no-daemon assembleDebug
```

On POSIX shells use `./gradlew`. Local success does not replace CI success.

## Reproducibility

- Toolchain versions are pinned in `gradle/libs.versions.toml`, `gradle/wrapper/gradle-wrapper.properties` and both workflows.
- Dependencies are resolved only from Google Maven and Maven Central.
- Signing credentials live solely in GitHub Actions secrets.
- Release tags, sources, artefacts, checksums and build provenance are retained in GitHub Releases.
- Gradle dependency verification metadata will be generated and committed when the dependency set stabilises; see the roadmap.
